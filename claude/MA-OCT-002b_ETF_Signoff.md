## Conditions (binding on the run sheet)
- **C-1 (code fix before M10; blocks M10 only).** In `holdings-pipeline.js` (lines 179–181), the new `measure` read (`getTodayWriteCount`, for `writes_today_after` and the last ETF's `w`) runs **before** the `etf_offset` / `last_run_status` saves. Holdings' own budget model runs close to the 50-subrequest limit (`MAX_BATCHES_PER_RUN = 35`). On a heavy Sunday, a monitoring read could therefore move the failure onto the cursor save and freeze the pass. **Fix:** move that read **after** the two `setPipelineState` cursor writes, and wrap it in `try/catch` so a failure only nulls `writes_today_after`. Then re-run `heartbeats-contract` (33/33). M6 (bootstrap) is not affected.
