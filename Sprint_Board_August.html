FAST-FOLLOW entity_master "holding" / "spv" types not produced by entities-seed.js
Resolved — Confirmed Benign ▶
Found during
MA-AUG-002 end-to-end verification, 29 July
Objective
entity_master has 4 rows typed "holding" and 1 typed "spv". entities-seed.js's classifyType() only ever assigns fund, government, or operating — so something else is setting these, most likely entities-enrich.js reclassifying off LEI legal-form data. Not yet confirmed by reading that code path directly.
Current status
Confirmed via direct code read, 1 August. "holding" is intentional: entities-enrich.js's Level 2 GLEIF parent-chain lookup auto-creates a new entity_master row with a hardcoded type='holding' whenever it discovers a direct/ultimate parent LEI not already in the table (line ~244) — expected behaviour, not a bug. "spv" is NOT produced anywhere: grepped entities-seed.js, entities-enrich.js, and entities-figi.js for "spv"/"SPV" — zero matches across all three. entities-figi.js is confirmed read-only against entity_master (never inserts). The single spv row predates the current pipeline code and is legacy/manually-seeded data, unrelated to any active Worker.
Decisions made
1 August — resolved by code inspection, no D1 query needed; no fix required, both findings are benign
Next step
None — closed. If the single legacy "spv" row ever causes a real issue, it can be manually reclassified.
